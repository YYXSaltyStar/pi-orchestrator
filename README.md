# pi-orchestrator

把 Pi 会话变成**只规划、不执行的编排者**，所有实际工作交给在独立进程中运行的子智能体。

这是一个 Pi 包，也是一次架构验证：**母智能体与子智能体之间的隔离，究竟能不能在 Pi 上做到、做到什么程度。**

---

## 它解决什么问题

一个直接调用工具的智能体，上下文里会不断累积原始内容——读过的文件、抓过的网页、命令的输出。任务一长，上下文被这些内容填满，费用上涨，行为也变得难以预测。

「母—子」架构的做法是：**母智能体只负责拆分任务和整合结论，具体操作全部委派出去。** 子智能体在自己的上下文里干完活，只回传一份简短的结构化报告。母智能体的上下文因此始终保持在很小的规模。

关键前提是**隔离**——子智能体不能继承母智能体的对话，母智能体也不该看到子智能体的全过程。否则上下文只是换了个地方堆。

---

## 两种隔离强度（本项目最重要的设计点）

| | 装配期硬剥夺 | 运行期软剥夺 |
|---|---|---|
| 触发方式 | `--tools read,grep,find,ls,subagent` | `PI_ORCHESTRATOR=1` |
| 强度 | **强**——工具定义从未进入上下文 | **弱**——定义可能已经进过 |
| 谁来执行 | `agent-lab/orchestrate.ps1` | `pi-orchestrator` 扩展 |
| 用在哪 | 正式用法 | 已开着的会话想切进编排模式 |

**为什么硬剥夺更强**：模型看不到某个工具的名字和参数格式，就不会去调用它——这不是"调用后被拒绝"，而是"根本不知道有这回事"。

软剥夺是在运行期把工具从活动集合里移除。此时工具定义可能已经出现在本次运行的上下文里了，所以它是补救措施，不是可靠边界。

这个区分来自课程讲义第七节：**限制一个智能体的能力，最可靠的位置在装配阶段；到了执行阶段再动手，已经晚了。**

## 组成

| 路径 | 作用 |
|---|---|
| `pi-orchestrator/extensions/subagent/` | 注册 `subagent` 工具，把任务派给独立进程 |
| `pi-orchestrator/extensions/orchestrator/` | 注入编排者身份 + 运行期软剥夺写工具 |
| `pi-orchestrator/extensions/guard/` | 检测工具投递失败，向 stderr 打标记 |
| `pi-orchestrator/prompts/orchestrator.md` | 编排者的系统提示词 |
| `pi-orchestrator/agents/` | 三个子智能体角色定义 |
| `agent-lab/` | 验证工程：输入、启动器、基准、产物 |
| `docs/` | 架构设计与 QE 跨环境方案 |

## 快速开始

前置：Pi 已安装并接好模型（`pi --version` 能跑）。

```powershell
# 1. 安装包（本仓库根目录下）
pi install .\pi-orchestrator

# 2. 把角色定义装到 Pi 的 agent 目录
mkdir -Force "$env:USERPROFILE\.pi\agent\agents" | Out-Null
copy .\pi-orchestrator\agents\*.md "$env:USERPROFILE\.pi\agent\agents\"

# 3. 运行编排者（硬剥夺）
cd agent-lab
.\orchestrate.ps1
```

一次性任务：

```powershell
.\orchestrate.ps1 -Task "分析这个目录的结构，汇总到 reports/REPORT.md"
```

### 可选的入口命令

```powershell
.\pi-orchestrator\_install-entry.ps1     # 安装 PATH shim
pi-orchestrator                          # 之后可直接调用
```

> `.cmd` shim 是 ANSI 编码，**中文参数写在 `.ps1` 里执行**，不要在交互式 cmd 里手打，
> 否则中文字面量会被破坏。

## 怎么向它下指令

子智能体**看不到母智能体的对话**，所以每条任务描述必须自包含。

```
✅ 派一个 doc-worker 分析 <绝对路径>\sec1.md，
   把 JSON 报告写到 <绝对路径>\reports\worker-sec1.json

❌ 分析刚才那个文件
```

写清三件事：**做什么、产出到哪、什么格式**。

除非你只想给目标、让它自己拆：

```
目标：把 sections/ 下的章节结构整理成 reports/FINAL.md，
包含标题数、表格行数、代码块数、插图引用数，并对数字做独立校验。
你可以用 subagent 把工作分派给 ~/.pi/agent/agents/ 下的角色。
完成后说明你如何拆分任务、为什么这么拆。
```

## 验证结果

`agent-lab/` 是一次完整跑通的记录：母智能体拆出 8 个子智能体（4 个 worker + 4 个 verifier），
加上 1 个 report-writer，产出 `reports/` 下的 9 份文件。产物已提交，可以直接看。

已验证的架构主张：

| 主张 | 证据 |
|---|---|
| 母智能体没有执行能力 | 工具集限定为 5 个，无 `write`/`edit`/`bash`/`powershell` |
| 母智能体必须委派才能产出文件 | 全部产物由子智能体写出 |
| 子智能体上下文隔离 | 母智能体只收到一句 `WROTE <path>` |
| 子智能体可自行决策 | worker 主动在 `anomalies` 里报告了行数口径歧义 |
| 独立校验能发现分歧 | 出现过 `mismatch` 判定 |

### 复现测试夹具

`sections/` 下的四个文件是课程讲义的章节摘录，**因为版权原因没有包含在本仓库中**
（已被 `.gitignore` 排除）。要从头复现：

1. 准备讲义 Markdown，按二级标题切出前四节
2. 存为 `agent-lab/sections/sec1.md` … `sec4.md`
3. 运行 `agent-lab\_prepare.ps1` 重算基准
4. 运行 `.\orchestrate.ps1` 执行编排任务

`reports/` 里已有的产物和 `_ground_truth.json` 里的基准数字都保留了，不重跑也能看懂验证结果。

## 已知限制（重要，别当它已经完备）

### 1. verifier 角色不可靠

实测中 `doc-verifier` 与 `doc-worker` **会犯同样的口径错误**——worker 算对了它误报，
worker 算错了它漏报，两种都出现过。

根因是**两个角色用的是同一套判断口径**。当口径本身有歧义（例如"表格数据行"是否
包含表头），同源的模型会系统性地犯同一个错——**独立复算纠正不了口径偏差**。

结论：**同源的两个模型不构成独立校验。** 真要严格，得用确定性的检查脚本，
而不是让另一个模型"再数一遍"。

### 2. guard 只保护母进程

`guard` 扩展检测到工具投递失败时只打标记、不修复；修复靠 `orchestrate.ps1` 的重试循环。
但**子智能体进程没有外层重试**。因此子智能体越多，整链失败概率越高。

未修，属已知脆弱点。

### 3. 工具投递故障是间歇性的，未定性

在 `deepseek` + Pi 的组合下，模型偶尔拿不到工具集：要么把工具调用写成纯文本，要么直接
说"我没有工具"。失败时 `getActiveTools()` 返回空数组——是工具真的没送到。

已排除：模型选择、提示词长度、任务复杂度、工具数量、特定工具组合。
未追根因（不在可修层），靠重试兜底。

### 4. 母智能体的「自由拆分」能力未单独验证

`agent-lab` 那次任务里，步骤、角色、产出路径都是**外部写死的**，所以验证的是
「能否按指令执行」，不是「能否自主拆分」。只给目标不给步骤的测试还没做。
